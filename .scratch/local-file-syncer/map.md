# Map: Local file syncer

Labels: `wayfinder:map`

## Destination

We know whether a free existing tool covers the need; if not, a build-ready spec exists at `.scratch/local-file-syncer/spec.md` for a general-purpose, offline, Windows-only file/folder sync tool: one master fans out one-way to many replicas grouped as sync rules, an on-demand check finds drift, and a GUI review screen syncs at any level of an expandable tree. Planning only — building the tool is a separate effort.

## Notes

- **Domain**: general local file/folder syncing. Driving use case: keeping Matt Pocock skill folders current across Claude Code projects, each project taking a different subset. Second use case: a master resume file mirrored into many directories. Vocabulary in `CONTEXT.md` (master, replica, sync rule, check, sync, drift, divergence).
- **Planning only.** This map ends at a spec. Do not implement the tool from these tickets.
- **Skills to consult each session**: `grilling` + `domain-modeling` by default; `research` for the tool survey; `prototype` for UI-shape questions.
- **Settled going in** (constraints, not open questions): one-way fan-out, master wins, no merge, no reverse push · one sync rule per syncable unit · Python + PySide desktop GUI · on-demand check only (no watching) · Windows only · human-readable config file + separate state file, both GUI-managed · content-based comparison (not timestamps) · first-time provisioning (missing replica) handled the same as an update · deletions propagate but are confirmed as a separate category.
- **Tracker**: local markdown (`docs/agents/issue-tracker.md`). This is not a git repo, so research findings are captured as files under this effort dir, not on a branch.

## Decisions so far

<!-- one line per closed ticket: gist of the answer, then the link for detail -->

- [Survey free tools for one-way fan-out sync with review](issues/01-free-tool-survey.md): build from scratch — no free/offline/Windows tool covers a one-master-to-many-replicas rule model with divergence flagging (FreeFileSync is closest but lacks both); check/copy engine is thin over the stdlib (`os.walk`, `hashlib`, `shutil`), no third-party sync library worth adopting. (`filecmp.dircmp` was named here but dropped by [Check engine — how drift is computed](issues/05-check-engine.md) — can't express a three-way baseline compare.)
- [Sync-rule config model](issues/02-sync-rule-config-model.md): `config.toml` (TOML) holding `version` + `[settings]` + `[[rule]]` blocks with `id` (immutable UUID4, joins to state), `name`, `master`, `master_type` (`dir`/`file`, stored), `replicas` (abs paths), `ignore` (reserved). Portable storage — every generated file (config, `state.json`, `backups/`, `logs/`) lives under the install dir (`base_dir`), never `%APPDATA%`/registry; `base_dir` must be user-writable (hard error if not). Replica identity = normalised abs path; replica and master paths unique across all rules (exact dupes blocked). Config is pure intent; `state.json` holds all last-sync data keyed by rule id + replica path. Atomic config writes. See [ADR 0001](../../docs/adr/0001-portable-self-contained-storage.md).
- [Divergence state model](issues/03-divergence-state-model.md): after each sync `state.json` records **one SHA-256 hash per file** (+ size/mtime as advisory re-hash-skip hints) — one hash, not two, because a completed sync makes replica == master. Check compares current master and current replica each against this baseline: M≠B & R==B → drift; M==B & R≠B → divergence (out of "sync all", → [06](issues/06-divergence-ux.md)); both changed & equal → converged; both changed & unequal → changed-on-both-sides; in B & gone from M → master-deleted (→ [08](issues/08-deletion-and-rename-handling.md)); no baseline entry → can't be divergence. `state.json`: `{version, hash_algo, rules:{<uuid>:{replicas:{<norm-path>:{last_sync, files:{<rel-path>:{hash,size,mtime}}}}}}}` — flat file map, no dir entries, keys keep master's case (matched case-insensitively on Windows). Writes commit-at-end via tmp+`os.replace()`; interrupted sync writes nothing (copied files re-sync harmlessly); partial syncs merge per-file; "skip" never writes the baseline. No baseline (first check / deleted / algo mismatch): empty replica → provision; replica with content → per-file confirm only, nothing in "sync all"; corrupt file → quarantined to `state.json.corrupt-<ts>`. No rolling backups of `state.json`.
- [Review-and-sync tree UI](issues/04-review-and-sync-tree-ui.md): **two-pane, rule-scoped** review screen (prototype: [`prototype/review_prototype.py`](prototype/review_prototype.py), variant D of 4). Left = list of sync rules with aggregate status; right = tree with **each replica a top-level branch**, then folders, then files, for the selected rule. One rule reviewed/synced at a time; roll-up spans that rule's replicas only. **One click = full tick + roll-down**; the tri-state dash is computed (some-but-not-all children ticked), never reachable by clicking. Three action categories kept apart: *safe drift* (`new`/`changed`) checkable and the only thing "Sync all safe" touches; *master-deleted* checkable but excluded from "sync all" and gated behind its own confirm ([08](issues/08-deletion-and-rename-handling.md) owns wording); *conflict* (`diverged`/`both_changed`/`no_baseline`) **not checkable at all**, display-only, "resolve → [06](issues/06-divergence-ux.md)". Large trees: default-expand only drift-containing subtrees, no virtualisation for v1. Button set / chrome deferred to [07](issues/07-gui-rule-management.md) + spec assembly. New glossary candidate: *safe drift*.
- [Check engine — how drift is computed](issues/05-check-engine.md): `os.walk` both sides (no `dircmp`), union with the baseline key set, categorise each file three-way `(baseline, master-now, replica-now)`. Compare size-then-SHA-256 (streamed); skip the re-hash when size **and** mtime both match the baseline. Full taxonomy: `in_sync` / `converged` / `new` / `changed` / `diverged` / `both_changed` / `no_baseline` / `master_deleted` / `replica_only` / `unreadable` — shown as **plain-text phrases, no glyphs** (corrects [04](issues/04-review-and-sync-tree-ui.md)). Locally-deleted replica file → `new`; master-deleted + replica-edited → `both_changed`. The **check never writes** — a `converged` file's stale baseline is refreshed on the next sync. Fixed symmetric built-in ignore list (`.git/`, `__pycache__/`, `~$*`, …); the `ignore` config key stays reserved. `os.walk(followlinks=False)`; read/permission errors collected per-path as `unreadable`, never fatal. Returns a flat per-replica `CheckResult` (all files, `in_sync` included); the UI builds its own roll-ups. Engine is a plain function with optional `progress` + `cancel` hooks (threading is [07](issues/07-gui-rule-management.md)'s). New glossary: *safe drift*, *converged*, *changed on both sides*. Spun off [Sync application — how ticked changes are executed](issues/10-sync-application.md).
- [Divergence UX](issues/06-divergence-ux.md): a **conflict** (`diverged`/`both_changed`/`no_baseline`) is never ticked in the tree; it's **resolved** through a dedicated dialog (per-file "Resolve", or a pageable queue via the replica branch's "Resolve conflicts"), offering **overwrite from master** / **skip for now** (pure no-op, re-flagged forever, no snooze) / **keep replica's version** (adopts replica as new baseline and sets a persistent **kept** flag, shown distinctly until real future master drift supersedes it) — each applying immediately, not staged for a later Sync. Real text diff per file (metadata-only fallback for binary/oversized), adapted per category (`diverged`: replica-vs-baseline; `both_changed`: two diffs; `no_baseline`: direct master-vs-replica, no history). Per-category bulk actions on the replica branch (`no_baseline` always excluded, per-file only); bulk overwrite requires its own confirm, bulk keep doesn't. Corrects [03](issues/03-divergence-state-model.md): `state.json` file entries gain an optional `kept` field. New glossary: *conflict*, *resolve*, *kept*.
- [GUI rule management & first-run](issues/07-gui-rule-management.md): rule actions live on both a toolbar row and a right-click context menu. First run = empty rule list + inline "+ Add rule" prompt, no wizard. Add/edit rule is one modal (not a wizard): explicit "Choose file…"/"Choose folder…" buttons set `master_type`; replicas added via browse, drag-and-drop of several at once, or a typed path (for not-yet-existing provisioning targets); add-replica-to-existing-rule reuses this same editor. Master path is immutable post-creation (delete + recreate to change it); replica edits stay remove-old+add-new per [02](issues/02-sync-rule-config-model.md). Deleting a rule (or removing one replica) purges its `state.json` entries immediately; every config load — not just GUI deletes — reconciles `state.json` against config, purging anything no longer referenced. `config.toml` is GUI-only in intent but tolerates hand edits (reload on startup + manual "Reload config", warns before clobbering external changes). Single-instance `syncer.lock`: a second launch blocks with a message and exits (no window-focus attempt); a stale lock (dead PID) is silently recovered. No new glossary, no ADR — checked via `domain-modeling`.
- [Deletion & rename handling](issues/08-deletion-and-rename-handling.md): no rename detection in v1 — always delete-old + create-new via the existing `master_deleted`/`new` categories. `replica_only` files (in replica, never in master, no baseline) are informational/display-only, never checkable or auto-deleted, same tier as `unreadable`. `master_deleted` files tick individually like safe drift but apply through one itemised batch-confirm dialog ("Yes, delete N files"). An emptied replica directory is removed silently as post-deletion cleanup once its files are confirmed-deleted. New rule-level state **master missing** (whole master root gone, not just individual files) blocks ordinary sync to prevent a one-click full-replica wipe from a bad path/unmounted drive; a one-time per-rule "unlock" (not persisted) drops the rule back into the normal tree. Corrects [04](issues/04-review-and-sync-tree-ui.md): rule list needs a distinct master-missing status. New glossary: *master missing*.
- [Sync application — how ticked changes are executed](issues/10-sync-application.md): new files copy straight in (`shutil.copy2`); overwrites go through a same-directory temp file + atomic `os.replace()`, cleaned up on failure, nothing to clean up on success. No case-correction (Windows stays case-insensitive; revisit only when a POSIX build exists). No `backups/` in v1 — `ADR 0001`'s directory stays reserved but unused. Deletes remove the file then prune newly-emptied replica directories upward to (not including) the replica root. Ordering: copies before deletes per replica; replicas and rules processed strictly sequentially, never in parallel. Partial failure: continue and collect errors, no rollback — failed files simply keep their pre-sync category next check. One plain-text run log per sync under `logs/` (per-file lines + a summary line). `state.json` commits once per replica immediately after it finishes, not buffered for the whole run. Executor signature mirrors `check()`: `sync(rule, applied_changes, progress, cancel)`; post-run a summary dialog shows outcome counts plus a scrollable error list.
- [Assemble the build-ready spec](issues/09-assemble-spec.md): destination reached — [`spec.md`](spec.md) assembles every resolved ticket into a build-ready spec, no new decisions made. Deferred fog (packaging/run model, large-folder performance, config/state migration) and the out-of-scope list are both carried forward into the spec's closing sections.

## Not yet specified

<!-- in-scope fog; graduates into tickets as the frontier advances -->

- **Packaging & run model on Windows** — how the tool is launched (plain Python script, PyInstaller exe, etc.). Gated on the build-vs-adopt outcome of [Survey free tools for one-way fan-out sync with review](issues/01-free-tool-survey.md). Narrowed by [Sync-rule config model](issues/02-sync-rule-config-model.md): portable "everything beside the executable" storage favours a PyInstaller one-folder build or a plain script; a one-file exe unpacks to a temp dir and fights that rule. Final call still deferred to the build effort.
- **Performance strategy for large folders** — hashing/walk cost on big trees, and (per [Review-and-sync tree UI](issues/04-review-and-sync-tree-ui.md)) whether the review tree needs virtualisation/lazy loading beyond v1's eager `QTreeWidget`. [Check engine — how drift is computed](issues/05-check-engine.md) built in the one perf lever for v1 — skip re-hashing a file whose size **and** mtime match the baseline — and shaped the engine for a worker thread (`progress` + `cancel` hooks). Everything past that (threaded hashing, incremental walk, tree virtualisation) stays here for the build effort.
- **Config versioning / migration** — how the config and state files evolve across tool versions.

## Out of scope

<!-- ruled beyond the destination; closed, never graduates -->

- Real-time / background watching of masters — on-demand check only for v1.
- Reverse or bidirectional sync (editing a replica and pushing back to the master).
- Three-way merge of conflicting edits.
- Non-Windows support (macOS, Linux).
- Network / cloud sync.
- Git operations (pulling the upstream Matt Pocock repo) — the user does this by hand.
